About me #

I worked at a Fortune 10 company for most of my career, where I did site reliability engineering for the reverse proxy behind a bunch of really big websites and over 2000 smaller ones, and where I built a data-lake-plus-feature-store for an ML organization.

What is pyinfra? #

pyinfra is a command-line tool that turns Python code into shell commands and runs them on your servers over SSH, in parallel. Think Ansible, but simpler.

deploy.py
for user in ['admin', 'alice', 'bob']:
    server.user(user)

files.put('files/hello.txt', '/etc/motd')

if host.data.get('install_postgres'):
    apt.install('postgresql')

Why use pyinfra? #

I chose pyinfra over Ansible because it has most of the latter's good parts, most importantly that it is declarative – you describe what a server should look like, and pyinfra makes it so. Like Ansible, it's also imperative – if a server is already in the desired state, nothing happens when you run it again.

Unlike Ansible, there's no YAML – deploys (playbooks) are written in Python, which means you can do anything you can do in Python: you can have fors and ifs, you can have code completion and type checking, and can even import libraries.

Of interest to people using Ansible at larger scales, pyinfra is also faster. In my limited, small-scale experience, it is even faster than Ansible with the Mitogen plugin.

In fairness to Ansible, while pyinfra has been around for 10 years, it has fewer built-in operations (modules) and a smaller ecosystem, although that's partially offset by how easy it is to write custom operations.

When to use pyinfra? #

The use cases for pyinfra follow from what it does, configure servers over SSH.

As such, it's a good fit for cloud-agnostic architecture. In the extreme case of one-computer programming, pyinfra still makes deploys reproducible and prevents drift, and you're likely to have development and pre-prod machines anyway. Due to its low learning overhead, it's also good for self-hosting and home lab settings.

Finally, if you don't use it for deployments, pyinfra gives you a convenient, reviewable way of running ad-hoc commands on a fleet of servers (say you have a memory leak and need to reload stuff once in a while until you find the root cause).

From simplicity also come limitations: it's harder to do fully-automated pipelines out of the box, and coordination is needed if multiple people run deploys at the same time. Nevertheless, you can get pretty far if you structure your deploys well, and pyinfra also has a Python API for when there's stuff you can't do from within deploy code.

Operations and facts #

First, we should get familiar with two basic pyinfra concepts.

Operations change the server; most operations are declarative and idempotent, and you use them to ensure state. A Python file containing operations is called a deploy.

Here's a simple deploy with one operation that says "I want hello.txt to exist":

examples/create_file.py
from pyinfra.operations import files

files.file('hello.txt', present=True)

If we run this deploy (here, on my @local machine), we see a list of all the operations and on which hosts they will produce changes, and are asked to approve them:

Facts gather data about the target host; you use them to control operations.

Here's a deploy that installs the Apache web server:

examples/install_apache.py
from pyinfra import host
from pyinfra.facts.server import LinuxName
from pyinfra.operations import server

if host.get_fact(LinuxName) in ['Ubuntu', 'Debian']:
    server.packages('apache2')
else:
    server.packages('httpd')

The package is called http by most package managers, but on Debian-based distributions it is called apache2; we use the LinuxName fact to detect where we are and pass the appropriate name to the server.packages operation.

Since my local machine is a Mac, we see the httpd branch is chosen (deploy code runs once per host, so you could have different branches on different hosts):

$ pyinfra @local examples/install_apache.py --dry
...
--> Detected changes:

    server.packages (httpd)   1 (@local)   -

Where are the commands? #

So, where are the shell commands?

Before we look at debug output, let's look at how pyinfra operations are implemented.

Here's a simplified version of the file implementation:

@operation()
def file(path: str, present: bool = True):
    info = host.get_fact(File, path=path)

    if info is None and present:
        yield f"touch {quote(path)}"

    elif info and not present:
        yield f"rm -f {quote(path)}"

The structure is similar for all operations: read the current host state using facts, diff it against the desired state, and return commands to reach the desired state, if needed.

Here's another deploy that says "I want hello.txt to not exist":

examples/delete_file.py
from pyinfra.operations import files

files.file('hello.txt', present=False)

With --debug, we can observe the commands being run during each execution phase.

During the prepare phase (before approval), pyinfra runs the deploy code once per host to load operations, and then runs each operation to see if it returns commands, without running the commands themselves (this is how "detected changes" works). Running operations also runs facts, which results in read-only commands being run:

Initial nginx setup #

OK, now we can become dangerous.

So far we've been using my local machine as a target, but we want beta to be as similar to prod as possible, so I've set up an Ubuntu 26.04 virtual machine using Vagrant.

We've also used pyinfra with a single host, but typically you will use an inventory file containing groups of hosts instead. For our demo, we need just one group:

infra/inventories/beta.py
# group_name = [host1, host2, ...]

# web_servers = [i.hostname for i in aws.ec2.list_instances(asg='my-asg')]

Since the inventory is a Python file, groups don't have to be static lists – you could, for example, import a library and list the instances in an cloud autoscaling group.

After we update the package cache, we install nginx, we disable the default "Welcome to nginx!" site, and then we reload the nginx config. To avoid unnecessary reloads after the first run, we use the _if global argument to reload only if the previous operation actually ran. In theory, we could use a fact to gate the last two operations instead:

apt.packages(...)
if host.get_fact(Link, '/etc/nginx/sites-enabled/default'):
    files.link(...)
    server.service(...)

...but that if happens in the prepare phase, when nginx hasn't been installed yet, so those operations will simply be skipped on the first run.

@deploy("nginx site")
def site(template, domain, **context):

    write_site = files.template(
        name="write",
        src=template,
        dest=f'/etc/nginx/sites-available/{domain}',
        domain=domain,
        **context,
    )
    enable_site = files.link(
        name="enable",
        path=f'/etc/nginx/sites-enabled/{domain}',
        target=f'/etc/nginx/sites-available/{domain}',
    )

    server.service(
        name="reload",
        service='nginx',
        reloaded=True,
        _if=any_changed(write_site, enable_site),
    )

Besides the decorator and the function definition, it looks like any other deploy; there's an operation to write the config from a template, one to symlink it into sites-enabled, and one to maybe reload nginx, just like before.

Another way to reuse stuff is via the files.template operation, which uses Jinja. Here, we have a base template for any HTTP site:

infra/templates/nginx/http.conf
server {
    listen 80;
    listen [::]:80;
    server_name {{ domain }};

    {% block server %}{% endblock %}
}

...that we extend with specific site configuration:

infra/templates/nginx/home.conf
{% extends 'templates/nginx/http.conf' %}

{% block server -%}

    location / {
        root /opt/home;
    }

{%- endblock %}

The question is, where do we store the secret key before we write the config?

The simple (and wrong) solution is to hardcode it in the deploy code; besides the whole unencrypted-secrets-in-version-control issue, beta and prod should have different secrets.

But as I said, a deploy is a Python file, so we can do anything: we could get secrets from a password manager, a security key, or even an encrypted file. To illustrate the point, here's a simple function that reads named secrets from a JSON file:

infra/modules/secrets.py
import json
from pyinfra import host

secrets_path = 'secrets.json'

def get_secret(name, *, stage=None):
    if not stage:
        stage = host.data.stage

    with open(secrets_path) as f:
        data = json.load(f)

    if secret := data.get(stage, {}).get(name):
        return secret

    raise RuntimeError(f"secret {name!r} for stage {stage!r} not found")

The stage comes from host data, this time not from the inventory, but from a group data file that applies to all hosts in a group (the inventory name is an implicit group):

infra/group_data/beta.py
stage = 'beta'

The config template looks like this:

infra/templates/config.py.jinja
SECRET_KEY = {{ '{!r}'.format(get_secret('app_secret_key')) }}
